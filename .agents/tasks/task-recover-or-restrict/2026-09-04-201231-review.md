# RECOVER-OR-RESTRICT (v2): re-review after fixes to webhook idempotency, dead risk signals, review guard and recovery actions

Second review pass over the deterministic subscription recovery/access-decision system after commit `a9c7e82`, which addresses the six issues raised in v1. Every prior issue is verified fixed against the code: webhook idempotency is now recorded only at terminal-success exits, the three tuned-but-unemitted risk signals (`recovery_failure`, `recovery_success`, `unpaid_renewal`) are now produced by `buildRiskSignals`, an optional timing-safe `REVIEW_SECRET` guard gates `/review` and `/explain`, the two orphaned `RecoveryAction` variants are now selectable, and the score-clamp / pattern-over-band behaviours are documented in the README and customer-detail UI. `npm run build` builds both workspaces, `npm test` is 133/133 across 10 files, and `npm run seed` matches all 7 scenarios (scenario 6 SUSPEND+blacklist, scenario 7 RECOVER-not-blacklist). The newly-emitted signals were the main regression risk; scenario 7 still lands at risk=0.2 / RECOVER / ACTIVE because the `recovery_success` trust credit offsets the `recovery_failure` penalty, so the central 6-vs-7 distinction still holds.

Watch for: no new blocking concerns. Two minor observations remain — (1) **confirmed** — the `unpaid_renewal` count in `buildRiskSignals` is unwindowed (all renewals vs all successes) whereas the `renewal_avoidance` pattern detector windows both to `windowDays`, so the two "mirrored" counts can diverge on long histories; behaviourally harmless because recency decay handles aging, but the code comment claims an exact mirror it doesn't strictly implement; (2) **confirmed** — the unknown-event path returns 500 (a Razorpay retry storm on a genuinely unrecognised event will keep 500ing rather than being acked), which is a deliberate and correct fail-loud trade-off but worth noting.

**Verdict**: APPROVED

## High-level view

The webhook idempotency fix is correct and well-placed. The route now only *checks* `hasProcessedWebhook` up front and calls `markWebhookProcessed` at each terminal-success exit: after a successful parse+ingest+evaluation, and after the "parsed fine but no linkable customer" 202 branch. Both the malformed-body (400) and unknown-event (500) paths leave the id unrecorded, so a corrected Razorpay retry of the same `x-razorpay-event-id` is processed; two e2e tests drive exactly these retry sequences.

The three previously-dead risk signals are genuinely emitted now. `buildRiskSignals` tracks an open-failure episode to emit `recovery_failure` on a repeated failed attempt and `recovery_success` (a negative-weight trust credit) on a success that clears an open failure, and derives `unpaid_renewal` from `renewal_due` events lacking a matching success. The one wrinkle is that the risk-path unpaid count is unwindowed while the pattern detector windows it (see issues).

The auth gap is closed with an optional shared secret: unset means open demo, set means `/review` and `/explain` require a length-guarded timing-safe match on `x-review-secret` or `Authorization: Bearer`. This is the human-gating control for blacklist, so gating it behind an opt-in secret (documented in `.env.example`/README, six negative-and-positive e2e tests) is the right resolution.

The two orphaned recovery actions are wired: `payment_reminder` is the INTERVENE-with-no-active-failure first touch, and `limited_grace_period` fires for insufficient-funds once both a delayed retry and an alternate route have been tried, each pinned by a decision test. The score clamp at 100 and the pattern-over-band decoupling are left as intended behaviour but are now explicitly framed as a bounded heuristic (not a probability) in both the README and the customer-detail page, resolving the "looks inconsistent" concern from v1.

### Webhook idempotency now records at terminal success only

The ordering flaw from v1 is gone. The handler checks `hasProcessedWebhook(eventId)` up front and returns the `duplicate` ack only if already processed; `markWebhookProcessed` is now called at each point where the event has been fully handled:

```
verify signature → check hasProcessedWebhook (no write) 
  → JSON.parse            (throw 400 on failure — id NOT recorded)
  → parseEvent            (throw 500 on unknown — id NOT recorded)
  → no linkable customer? → markWebhookProcessed + 202   ← terminal success
  → ingest + reevaluateAndPersist
  → markWebhookProcessed + 200 processed                 ← terminal success
```

The "accepted_unlinked" branch marking the id is deliberate: a parsed event with no linkable customer has nothing more to do on retry, so deduping it is correct rather than a leak. The 400/500 failure paths leave the id unrecorded, and the two new e2e tests (`malformed body then retry`, `unknown event then retry`) confirm the retry is processed rather than silently deduped.

### The three previously-dead signals are emitted and asserted

`buildRiskSignals` walks the chronologically-sorted payments carrying a `failureOpen` flag: a `payment_failed` on an already-open episode (or `attempt >= 2`) adds `recovery_failure` on top of the base `failed_payment`; a `payment_succeeded` that clears an open failure adds `recovery_success` (base weight −8, a trust credit) and closes the episode. `unpaid_renewal` is derived from `renewal_due` events lacking a matching success. `engine.index.test.ts` asserts each `signal_<kind>` evidence entry appears (and does *not* in the negative cases), including that `recovery_success` carries a negative weight and `unpaid_renewal` a positive one.

The regression check that matters: scenario 7 (`legitimate_repeated_failures`) now emits a `recovery_failure` at `pl4` (attempt 2) but also a `recovery_success` at `pl5` (the clearing payment). The seed still reports risk=0.2 / RECOVER / ACTIVE — the trust credit and tenure offset absorb the added penalty, so the genuine-recovery case is not pushed up a band by the new signals. Scenario 6 still pins at 100 / SUSPEND / blacklist. The distinction the product hinges on survives the change.

The divergence to flag: the pattern detector's `unpaidRenewals` windows both `renewal_due` and `payment_succeeded` to `windowDays`, while the risk-path count is unwindowed (all-time renewals minus all-time successes) and relies on recency decay to age old signals. The inline comment says the risk signal "mirrors the renewal_avoidance pattern detector's own count" — it approximates it but isn't the same arithmetic, so on a long history with old paid renewals the two counts can differ. Harmless to the score (decay dominates), but the comment overstates the equivalence.

### Optional review guard closes the auth gap without breaking the demo

`makeReviewGuard` reads `x-review-secret` or a `Bearer` token and guards on equal buffer length before `timingSafeEqual`, avoiding the classic throw when lengths differ. It is applied to `/explain` and `/review` — the two mutating routes — while the read-only GETs stay open. Six e2e tests cover the unset (open) case and the missing/wrong/correct-credential cases on both routes.

### Tests are behavioural and cover the new paths

The suite grew from 116 to 133 across a new `engine.index.test.ts` plus additions to `api.e2e.test.ts` and `decision.test.ts`: the two idempotency-non-poisoning retry sequences, the negative-auth cases on both guarded routes, the three signal-emission assertions with their weight signs, and the two recovery-action branches (reminder chosen, not repeated when already attempted, grace period only after the escalation chain). The unknown-event e2e logs an `Unhandled error` to stderr — the central error handler firing on the deliberate 500, not a test failure. Not separately tested: the unwindowed-vs-windowed unpaid-renewal divergence (no test exercises a long history where the two counts differ), which is why it stays an observation rather than a confirmed behavioural defect.
