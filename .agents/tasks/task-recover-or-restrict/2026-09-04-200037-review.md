# RECOVER-OR-RESTRICT: deterministic decision engine, Razorpay/OpenRouter adapters, dashboard

The build implements a subscription revenue-recovery and access-decision system whose financial, risk and decision logic is fully deterministic and rules-based, with the LLM confined to phrasing explanation/recovery text behind a deterministic fallback. The engine pipeline (classify → weighted recency-decayed risk → behavioural patterns → RECOVER/INTERVENE/RESTRICT/SUSPEND decision → access-state machine) is pure and side-effect free; persistence, the REST API and the two adapters wrap it without leaking into it. The seven demo scenarios are evaluated through the real engine at seed time and assert their expected outcomes, and the whole suite (build, 116 tests, 7-scenario seed) passes. The central product claim holds in practice: scenario 6 (grace-period value extraction) suspends with a blacklist *recommendation*, while scenario 7 (genuine repeated failures) recovers and is explicitly not blacklisted.

Watch for: (1) **confirmed** — the webhook route records the event id for idempotency *before* JSON parsing and event normalisation, so a delivery that fails parsing is permanently deduped and a Razorpay retry of the same event id is silently dropped; (2) **confirmed** — three risk-signal kinds (`unpaid_renewal`, `recovery_success`, `recovery_failure`) carry tuned weights but are never emitted by the orchestrator, so `renewal_avoidance`'s unpaid-renewal detection never reaches the risk score; (3) **confirmed** — every mutating endpoint (merchant review/blacklist approval, explain) is unauthenticated, and the merchant-review trust boundary is enforced only by the absence of a caller.

**Verdict**: NEEDS_CHANGES

## High-level view

The deterministic core is genuine. Risk is a weighted sum of per-signal contributions each multiplied by an exponential recency weight (30-day half-life) plus a capped tenure credit, not a raw event counter; a lone recent failure stays well inside the low band while stacked recent avoidance saturates the score. The decision rules key off risk band, avoidance-pattern severity and failure class in a most-severe-first cascade, and blacklist is only ever a boolean recommendation set on SUSPEND — never an auto-applied state. The access-state machine treats a successful payment as the dominant recovery signal (restoring ACTIVE) except when the decision is SUSPEND.

The Razorpay adapter is faithful: HMAC-SHA256 over the raw body, timing-safe hex comparison with a length guard, fail-closed on a missing secret/signature, only real event names, idempotency via `x-razorpay-event-id`, simulation mode by default with no invented gateway calls. The webhook route is correctly ordered before `express.json()` with a raw body parser so the verified bytes match what was signed. The one flaw is *when* idempotency is recorded relative to parsing (see issues).

The OpenRouter adapter degrades to the deterministic explainer on missing key or any network/parse/non-2xx error, and decisions never depend on it. The revenue engine is a pure aggregation into recovered/at-risk/pending/lost buckets with a heuristic predicted-failures list, honestly labelled as such.

Known gaps are unused risk-signal weights and unused recovery-action variants (dead enum members that don't affect current behaviour), a hard clamp of the risk total at 100 (so the score saturates rather than normalises), and no authentication on any route — the last is disclosed in the README's limitations but still matters because the merchant-review boundary is the mechanism that keeps blacklist human-gated.

<summary>Issues (6)</summary>

1. **Webhook idempotency recorded before processing** — `markWebhookProcessed(eventId)` runs before `JSON.parse` and `parseEvent`, so a body that fails parsing (invalid JSON → 400, unknown event → 500) still marks the id seen; a legitimate Razorpay retry is then deduped and never processed. Record the id only after successful processing, or roll it back on failure.
2. **Unused risk-signal weights** — `unpaid_renewal`, `recovery_success`, `recovery_failure` have `BASE_WEIGHTS` but are never emitted by `buildRiskSignals` in `engine/index.ts`; the `renewal_avoidance` pattern detects unpaid renewals yet that signal never reaches the risk score. Either emit these signals or drop the dead weights.
3. **No authentication on mutating endpoints** — `/api/customers/:id/review` (blacklist approval/rejection, access restore) and `/explain` are unauthenticated; the merchant-review trust boundary that keeps blacklist human-gated is enforced only by no one calling it. Disclosed in README limitations, but should gate these routes before any non-demo use.
4. **Unused recovery-action variants** — `payment_reminder` and `limited_grace_period` are valid `RecoveryAction`s with phrasing but are never selected by `chooseRecoveryAction`. Remove or wire them so the action space matches what the engine can actually recommend.
5. **Risk score hard-clamped at 100** — `clamp(totalWeighted, 0, 100)` saturates rather than normalises; scenario 6 pins at exactly 100 and any distinction above the cap is lost. Fine for banding, but the numeric score is not a calibrated probability and shouldn't be read as one.
6. **RESTRICT can fire in the low risk band** — scenario 4 restricts at risk=31 (low band) because a strong avoidance pattern alone triggers RESTRICT. Intended and correct, but the score/decision decoupling means the displayed band can look inconsistent with the outcome; worth a UI note.

### Risk scoring is genuinely weighted and recency-decayed

`computeRiskScore` (`engine/risk.ts`) multiplies each signal's base weight by `0.5 ^ (ageDays / 30)` and a magnitude, sums them, adds a tenure credit capped at −6, then clamps to 0..100. It is not a counter, and the unit tests pin the decay and tenure behaviour rather than fixed numbers.

Two caveats. The total is hard-clamped at 100 rather than mapped through a saturating function, so the score is a bounded heuristic, not a probability — scenario 6 sits at exactly 100. And `unpaid_renewal`, `recovery_success`, `recovery_failure` have weights but are never produced by `buildRiskSignals`; the risk unit test feeds `unpaid_renewal` directly to reach the high band, so the weight is exercised in isolation but is dead in the real pipeline. The `renewal_avoidance` pattern computes an unpaid-renewal count for its own severity but never emits a corresponding risk signal, so unpaid renewals influence pattern severity but not the risk score.

### Decision cascade separates genuine failure from avoidance

`decide` (`engine/decision.ts`) evaluates most-severe-first: high-confidence abuse (`high_confidence_avoidance` class, or high band + ≥2 strong avoidance patterns, or score ≥80 + max avoidance severity ≥0.8) → SUSPEND + `blacklistRecommended=true`; then high band / any strong avoidance / `suspicious_behaviour` → RESTRICT; then medium band / any avoidance severity / non-genuine failure → INTERVENE; else RECOVER. Genuine failure classes (`transient_recoverable`, `insufficient_funds`, `invalid_or_expired_method`, `authentication_required`) route to RECOVER with a next-best action even after repeats, which is why scenario 7's expired-card-then-issuer-outage sequence recovers instead of escalating.

The classifier only escalates a *transient* class to `suspicious_behaviour`/`high_confidence_avoidance` when the same failure code repeats ≥3/≥5 times; scenario 7's failures use two different codes, so no escalation fires and the terminal success drives ACTIVE. This is the mechanism that makes the 6-vs-7 distinction real rather than cosmetic.

RESTRICT can occur in the low risk band (scenario 4, risk=31) because `strongAvoidance.length >= 1` triggers RESTRICT independent of band. This is the intended pattern-over-score design, but it decouples the displayed risk band from the outcome and could read as inconsistent in the UI.

### Blacklist is genuinely gated behind human review

Blacklist appears only as `decision.blacklistRecommended` (set solely on the SUSPEND branch) and is surfaced alongside SUSPENDED — `transition` never advances to `BLACKLIST_RECOMMENDED` automatically. The only path into that state is the merchant explicitly calling `/api/customers/:id/review` with `approve_blacklist`, which writes an access-state-history row and audit entry; `reject_blacklist` eases to RESTRICTED instead.

The caveat is that the review route has no authentication, so "merchant-approved" is enforced only by the absence of an unauthorised caller. Since the human-gating of blacklist *is* the security control here, it belongs in the security posture, not only in a general README disclaimer.

### Webhook verification is correct; idempotency ordering is not

```
express.raw({type:"*/*"})  →  verifyWebhookSignature(rawBody, X-Razorpay-Signature)
   → markWebhookProcessed(eventId)   ← records id here
   → JSON.parse(rawBody)             ← can throw 400
   → parseEvent(payload)             ← throws on unknown event (500)
   → ingest + reevaluateAndPersist
```

Signature handling is right: `computeWebhookSignature` is HMAC-SHA256 over the exact raw bytes, compared via `timingSafeEqual` after a length guard, failing closed when secret or signature is missing; the route sits before `express.json()` and accepts only real event names.

The problem is ordering. `markWebhookProcessed` inserts the event id (returning `true` on first sight) *before* parsing. If `JSON.parse` throws or `parseEvent` rejects an unrecognised event, the request errors out but the id is already persisted. Razorpay retries deliver the same `x-razorpay-event-id`; on retry `markWebhookProcessed` returns `false` and the handler acks 200 `duplicate` without ever processing the event. Fix by recording the id only after successful processing, or deleting/rolling back the row on the failure paths.

### Tests are behavioural, not vacuous

The suite would fail if the logic regressed: risk tests assert half-life decay and tenure credit rather than fixed numbers; decision tests are table-driven across all four outcomes plus action escalation; the Razorpay test independently recomputes the HMAC, rejects tampered body and wrong-secret signatures, verifies fail-closed behaviour, and asserts unknown event names throw. Not tested: the webhook idempotency-before-parse failure path (no test drives a malformed body through the route and then retries the same event id), and the auth posture of the mutating endpoints (no negative-auth tests, consistent with there being no auth).
