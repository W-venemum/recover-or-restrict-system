# Placeholder OpenRouter key treated as unset + e2e fallback coverage (v2)

The follow-up commit (`22f4b53`) resolves both non-blocking findings from the v1 review. `loadConfig()` now treats the shipped `PASTE_YOUR_OPENROUTER_API_KEY_HERE` placeholder as absent, restoring the pure-deterministic zero-config demo the README promises, while a genuine key is honored unchanged. A new end-to-end `/explain` test wires a real `OpenRouterAdapter` with a mocked HTTP-401 fetch and asserts the honest `source: "deterministic"` + `fallbackReason` provenance surfaces through both the HTTP response and the audit entry. The deterministic engine, risk/decision thresholds, and the 7 seeded scenario outcomes are untouched; secret handling is unweakened.

Watch for: nothing blocking. One minor observation — the `"paste_your"` substring match is intentionally broad and would suppress a real (if implausible) key literally containing that substring (confirmed, low-risk by design).

**Verdict**: APPROVED

## High-level view

Finding 1 is fixed at the config boundary rather than by editing the shipped placeholder value. `isPlaceholderOpenRouterKey()` normalises the raw key and returns true on an exact case-insensitive match of the sentinel or on any value containing `paste_your`; `loadConfig()` maps such values to `undefined`, so `enabled` becomes false and `createLlmAdapter` returns the deterministic adapter. A genuine `sk-or-...` key flows through unchanged, so honest source/model reporting and OpenRouter enablement are preserved. Verified by reverting the fix: the two placeholder config tests fail (`enabled` true instead of false) while the genuine-key test still passes.

Finding 2 is fixed with a dedicated e2e test that builds a separate `createApp` wired to a real `OpenRouterAdapter` whose injected fetch always returns HTTP 401 — no network. It asserts the response and the persisted audit both report `source: "deterministic"`, the configured model, non-empty text, and a `fallbackReason` matching `/HTTP 401|network error/`, and that the API key never appears in either. Verified meaningful: reverting the `app.ts` provenance wiring to the old `llmAdapter.kind` behaviour makes this test fail (`source` reported as `openrouter`).

The follow-up commit touches only `server/src/config.ts`, `server/test/config.test.ts`, `server/test/api.e2e.test.ts`, and a comment-only change to `.env.example`. No engine, risk, decision, classifier, decay, or revenue file is in the commit, and `npm run seed` still prints all 7 scenarios matching their intended outcomes. `npm test` is 150/150 across 11 files; the intentional `payment.definitely_not_real` stderr line and the HTTP 401 fallback `console.warn` lines are expected negative-path output, not failures.

### Placeholder detection restores the deterministic default without editing the shipped value

The fix intercepts the key after `readString("OPENROUTER_API_KEY")` and before the `openRouter` config object is built. `isPlaceholderOpenRouterKey()` trims and lowercases, then matches either the exact sentinel or any value carrying the `paste_your` substring; a match collapses the key to `undefined`, which drives both the omitted `apiKey` and `enabled: false`. Because the shipped `.env` and `.env.example` still carry `PASTE_YOUR_OPENROUTER_API_KEY_HERE` verbatim, the zero-config runtime now selects the `DeterministicExplainer` again — the posture the base branch had before the cwd-independent `.env` fix started loading the root file. A genuine `sk-or-...` key is not a placeholder, so it still sets `apiKey` and `enabled: true`; the v1 honest `CompletionOutcome` → `LlmResult` reporting is untouched.

The one behavioural edge is the deliberately broad substring test: a real credential that happened to contain `paste_your` anywhere in its text would be misclassified as a placeholder and disable OpenRouter. This is a false-negative-only failure (it never enables OpenRouter for a placeholder), it is documented in the helper's comment, and no real OpenRouter key format contains that substring, so the risk is negligible. (confirmed)

### e2e fallback test exercises the app-level provenance wiring

The v1 gap was that the `app.ts` code deriving `source`/`model`/`fallbackReason` from the explanation result — and threading them into both the response and the audit entry — was only covered at the adapter unit level. The new test closes this by driving a full HTTP request through a real adapter whose fetch is mocked to 401, then asserting the response carries `source: "deterministic"`, `model: "openai/gpt-4o-mini"` (the configured model still named for the UI), non-empty explanation and recovery text, `outcome: "RECOVER"`, and a `fallbackReason` matching `/HTTP 401|network error/`. It then reads back the `explanation_generated` audit entry and asserts the same `source`/`model`/`fallbackReason`. The existing deterministic-intended `/explain` e2e assertion (no `fallbackReason`) is retained, so both branches of the response shape are now pinned. On the secret-handling boundary, the test also asserts the configured key (`sk-or-test-key-not-real`) appears in neither the response body nor the audit metadata JSON — a regression that interpolated the key into either would be caught.

The provenance is still taken solely from the `explainDecision` result while `draftRecoveryMessage` runs concurrently and its provenance is discarded — the same asymmetry noted in v1. Both calls share one adapter and config so they degrade together in practice; the follow-up neither introduces nor worsens this, and it remains a latent-only concern. (confirmed)
