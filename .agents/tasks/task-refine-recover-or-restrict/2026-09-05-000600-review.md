# OpenRouter transparency, cwd-independent env loading, and revenue-recovery UI framing (v1)

This refinement makes the LLM layer honest about what actually produced each explanation, fixes `.env` loading so the canonical repo-root file is found regardless of working directory, and reframes the dashboard and customer-detail UI around the revenue-recovery story while keeping the deterministic decision engine visibly separate from AI phrasing. The LLM adapter now returns a structured `{text, source, model, fallbackReason?}` per call, `/api/health` and `POST /explain` report the true runtime source and model, and a failed OpenRouter call is reported as `deterministic` with a non-secret reason instead of masquerading as a successful completion. The engine, financial, risk, and decision code is untouched; the revenue change is a pure pass-through of an already-stored `recommendedAction`.

Watch for: the config fix changes which `.env` is loaded, and the shipped root `.env`/`.env.example` carries a placeholder OpenRouter key that is treated as "enabled" — so the default demo now selects the OpenRouter adapter and every explain call 401s and falls back visibly, rather than running as a pure deterministic adapter (possible). Everything else — secret handling, honest reporting, scenario preservation, and the merchant blacklist boundary — holds up.

**Verdict**: APPROVED

## High-level view

The transparency change is the heart of this diff. `complete()` was rewritten from a swallow-all-errors `Promise<string | undefined>` into a structured `CompletionOutcome` that distinguishes success (carrying the model the API actually used) from failure (carrying a non-secret reason). Callers propagate that provenance up through `LlmResult`, and `/explain` reports the real `source`/`model` plus an optional `fallbackReason`. This closes the prior dishonesty where `source` was always `llmAdapter.kind` regardless of whether the LLM call actually succeeded.

Secret hygiene is careful and verifiable: failure reasons are limited to HTTP status, a safe network-error message, or fixed strings like `empty completion`; response bodies and headers are never read into logs, and a test explicitly asserts the API key never appears in `fallbackReason`. No real key exists in tracked files — only the `PASTE_YOUR_...` placeholder in `.env.example`, and `.env` is gitignored and untracked.

The config fix anchors `.env` resolution to the module's own location (two levels up) instead of `process.cwd()`, so `npm run dev:server` (cwd `server/`) now finds the repo-root file. One side effect deserves attention: because the placeholder key is a non-empty string, `enabled` becomes true and the default demo now runs the OpenRouter adapter (401 → visible deterministic fallback) rather than the pure deterministic path it took before.

The engine is genuinely untouched — `revenue.ts` only appends an optional `recommendedAction` copied straight from the stored decision view, with the ranking math unchanged, and the seed still prints all 7 scenarios matching expectations. The UI work is presentation-only: the dashboard leads with recovered/at-risk/rate/pending and a priority table with a "why prioritized" phrase derived from existing fields, and customer detail separates the deterministic "Decision engine — behavioural evidence" section from the "AI explanation" section, labeling deterministic fallback text as not LLM-generated. The merchant blacklist boundary is unchanged; the review route was not modified.

### Honest source/model reporting via `CompletionOutcome` → `LlmResult`

The old `complete()` returned `string | undefined` and callers did `text ?? fallbackSync()`, which lost all knowledge of whether the LLM actually answered — and `/explain` then reported `source: llmAdapter.kind` unconditionally, so a 401 that fell back to deterministic text was still reported as an OpenRouter response. The rewrite splits the outcome into `{ ok: true; content; model }` and `{ ok: false; reason }`. On success the adapter reports `source: "openrouter"` and the model the API actually used, falling back to the configured id only when the response omits `model` (which matters for routing aliases like `openrouter/free` that resolve to a concrete model). On any failure it returns the deterministic text with `source: "deterministic"`, the configured model string so the UI can still name it, and a `fallbackReason`; `app.ts` derives all three from the explanation result and both returns them and records them in the audit entry.

One asymmetry: the response headline `source`/`model`/`fallbackReason` are taken solely from the `explainDecision` result; `draftRecoveryMessage` runs concurrently and its own provenance is discarded. Both calls share the same adapter and config so they degrade together today, but if they ever diverged (one succeeds, one 401s) the reported provenance would reflect only the explanation.

### Non-secret failure diagnostics

The failure reasons are constrained to safe values: `no API key configured`, `HTTP <status>`, `network error: <err.message>`, `invalid response JSON`, and `empty completion`. The code deliberately does not read the response body on a non-2xx (a comment notes the body may echo request content) and never logs headers, the key, or the prompt. The test `never leaks the API key in the fallbackReason` asserts the key is absent from the reason on a 500, which would fail if someone later interpolated the response or request into the message.

### cwd-independent `.env` loading and its side effect

Resolving `.env` from `path.resolve(moduleDir, "..", "..", ".env")` handles both `server/src/config.ts` (register hook) and `server/dist/config.js` (compiled), and preserves dotenv precedence (no `override`). The `config.test.ts` suite is a genuine regression test: it spawns the config module with cwd set to both `server/` and the repo root and asserts identical results, and — most convincingly — builds a throwaway module tree with a sentinel `OPENROUTER_MODEL` in a sandbox root `.env`, runs it with cwd at the sandbox `server/`, and asserts the sentinel is read. That last test would fail under the old cwd-based resolution, so it meaningfully guards the fix.

The side effect: the base branch, under `cwd=server/`, loaded no `.env` (there is no `server/.env`), so `OPENROUTER_API_KEY` was `undefined` and `createLlmAdapter` returned the deterministic adapter. Now the root `.env` is loaded, and since `readString` returns any non-empty trimmed value, the `PASTE_YOUR_OPENROUTER_API_KEY_HERE` placeholder counts as a configured key: `enabled` is true and the OpenRouter adapter is selected. `/api/health` will report `aiMode: "openrouter"` and `model: "openai/gpt-4o-mini"`, and each `/explain` will attempt a real call that 401s and degrades to deterministic text with `fallbackReason: "HTTP 401"`, emitting a warn per call. Nothing is incorrect — the honest-reporting design surfaces the degradation — but the default demo posture changed from "pure deterministic" to "OpenRouter-attempting-then-falling-back." If the demo is meant to look deterministic out of the box, treating an obvious placeholder as unset (or documenting the new default) would avoid confusion. Confidence: possible — depends on the placeholder being present in the runtime `.env`, which is the shipped/`.env.example` default.

### Revenue pass-through leaves ranking untouched

`summariseRevenue` gains only an optional `recommendedAction` spread onto each `HighPriorityCustomer`, copied from `view.recommendedAction` (already present on `RevenueDecisionView` in the base). The priority computation, bucketing, and ordering are unchanged. The `revenue.test.ts` addition asserts the field is passed through for rows that have it (`c3` → `update_payment_method`, `c2` → `retry`) and stays absent for `c4`, and the existing strict-descending priority-ordering test still passes — so a regression that dropped the field or perturbed ranking would be caught. `npm run seed` still prints all 7 scenarios matching expectations, confirming no decision-path drift.

### UI separation of engine vs. AI, and honest badges

When `source === "deterministic"` the UI shows a "Deterministic fallback" badge, the model, the `fallbackReason` when present, and a note that no live LLM text was used — matching the backend's honest reporting rather than overstating AI involvement. The dashboard `ModeStrip` reads `/api/health` and shows payment mode, AI mode, and model from actual runtime state; `priorityWhy` derives its phrase purely from the row's `outcome` and `riskScore` (no fabricated data). The blacklist restriction copy ("recommended for human review, never auto-applied") reinforces the merchant-approval boundary. `web/src/api/types.ts` was updated in lockstep with the new `HealthResponse`/`ExplainResponse` fields.

### Blacklist boundary and review route

The merchant review/blacklist route in `app.ts` was not modified by this diff, so the human-approval boundary is preserved. The one audit-related change is the explanation audit entry, which now records the true `source`/`model` and an optional `fallbackReason` — an improvement to the audit trail, not a change to the approval flow.

### Tests

Coverage went from 133 to 146 passing across 11 files. New/updated tests: adapter success path (reports `openrouter` + API-returned model; falls back to configured model when `model` omitted; exposes the `model` getter), adapter failure paths (401 → `HTTP 401`, thrown fetch → `network error: ECONNREFUSED`, whitespace content → `empty completion`, key never leaked), the config cwd-independence suite, the revenue pass-through, and e2e assertions that `/api/health` exposes `aiMode`/`model` and `/explain` reports `source`/`model`/`outcome` with no `fallbackReason` in the deterministic-intended path. All use mocked fetch — no network.

Not tested: an end-to-end `/explain` call where the *configured* adapter is OpenRouter but the call fails, asserting the API response carries `fallbackReason` and `source: "deterministic"`. The adapter-level failure tests cover the provenance logic and the e2e test covers the deterministic-intended shape, but the `app.ts` wiring that surfaces `fallbackReason` into the HTTP response (and audit metadata) is not exercised end to end with a failing mocked fetch. A regression that dropped `fallbackReason` from the response body would not be caught.
